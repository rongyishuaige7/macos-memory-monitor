# v1.0.6j：菜单栏弹窗可达性与登录启动状态传播

## 范围

本阶段收口菜单栏弹窗在内容变长、使用较大字体或切换到历史视图时的可达性，并修复登录启动状态在弹窗中的观察边界：

- 将弹窗的页眉、视图切换和 footer/退出入口保持在稳定的外层结构中；中央内容使用受限的垂直滚动区域，避免长推荐、诊断提示或大字号内容把退出入口推出窗口；
- 集中定义弹窗宽度、最大内容高度和最小可用边界，供 SwiftUI 布局与纯值测试共同使用；
- 让 `MonitorPopover` 直接观察 `LoginLaunchCoordinator`，健康图标和健康 sheet 复用同一个注入实例；弹窗出现时刷新登录启动状态，并在应用重新激活时再次刷新，以发现系统设置中的外部变更；
- 增加布局策略边界测试、长内容受限高度 fixture 测试，以及登录启动状态发布/刷新回归覆盖。

## 非目标

- 不改变登录启动注册、注销、取消、错误保留或系统设置跳转语义；
- 不修改采样频率、进程/工作组排序、历史数据格式、详情页状态语义或权限策略；
- 不引入第三方 UI 依赖，不重做菜单栏视觉风格，不改变正式 Application Support、登录项、TCC/隐私权限或现有桌面实例；
- 不把自动化尺寸 fixture 当作真实窗口可滚动性的充分证明；稳定登录桌面会话中的 AX 末端/退出按钮检查仍需单独记录。

## 架构

1. `MonitorPopover` 新增 `@ObservedObject var loginLaunch`，由 `MemoryMonitorApp` 注入 `applicationDelegate.model.loginLaunch`。健康状态计算显式触碰该对象的已发布字段，避免只依赖 `MonitorViewModel` 对嵌套对象的间接读取。
2. 弹窗根结构采用固定页眉和 footer，中间的实时/历史内容放进一个受限高度的垂直 `ScrollView`。实时排行和历史图表保留各自必要的内部列表滚动；这种嵌套滚动风险在验证记录中明确，不通过改变数据模型来规避。
3. `MonitorPopoverLayoutPolicy` 作为无副作用纯值策略，负责清洗无效尺寸、暴露生产默认值并计算中央滚动区的最大高度。视图只使用策略输出，不散落数字常量。
4. 弹窗 `.onAppear` 和应用激活事件调用 `loginLaunch.refreshStatus()`。刷新仍由协调器的 `isUpdating` 门槛串行保护，不主动修改系统登录项。

## 风险

- 菜单栏窗口的可用高度受屏幕、菜单栏位置和系统字体设置影响；中央滚动区必须有有限上限，且 footer 不得被固定高度内容裁剪；
- 实时排行/历史图表已有内部 `ScrollView`，外层滚动可能产生嵌套手势竞争；应通过长内容 fixture、键盘/辅助功能可达性检查和稳定桌面 AX 复核观察；
- 应用激活通知可能在弹窗关闭时触发，刷新必须保持轻量、幂等且不与进行中的注册/注销操作竞争；
- SwiftUI 视图生命周期可能重复调用 `onAppear`，不得在其中启动长期任务或改变注册状态。

## 验证标准

- 布局策略测试覆盖默认值、有限/无限/NaN/负数输入、中央高度不超过上限以及页脚可用的最小内容高度；
- 长内容和大字号 fixture 在受限 viewport 下宽高有限、中央区域可滚动，footer fixture 仍被布局；
- 登录启动协调器在外部状态变化后刷新并发布新状态，进行中更新不会被被动刷新打断；弹窗源码复核确认健康 sheet 与健康图标使用同一注入实例；
- `swift test --package-path . --parallel`、严格并发 Debug/Release 构建、`./scripts/verify-release.sh`、`git diff --check` 全部通过；
- 不修改既有未跟踪探针/临时目录或正式实例；若桌面 AX 会话不稳定，只记录未验证，不伪造通过结论。

## 分阶段交付

1. **设计契约**：提交本文档，冻结滚动边界、状态观察和验证证据要求。
2. **源码与测试**：实现布局策略、弹窗结构、登录启动直接观察/刷新和回归测试，单独提交并推送。
3. **验证记录**：运行 targeted/full tests、严格构建和发布门禁，新增验证记录并单独提交、推送。
4. **桌面复核**：在稳定登录桌面会话中只读检查弹窗滚动末端、footer/退出按钮和健康状态更新；不稳定会话保留为待验证项。
